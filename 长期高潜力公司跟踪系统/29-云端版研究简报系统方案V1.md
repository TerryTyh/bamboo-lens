# 云端版研究简报系统方案 V1

版本日期：2026-04-14

## 一、为什么现在要转向云端

当前本地版已经验证了三件事：

1. 研究框架本身是成立的。
2. 简报格式和动态跟踪逻辑是可用的。
3. 本地门户适合作为阅读和沉淀入口。

但本地自动化存在一个根本性问题：

- 电脑不开机、睡眠、Codex 未运行时，定时任务无法稳定执行。

这意味着它可以作为验证环境，但不能作为正式的日常推送系统。

所以后续的正确方向不是继续修本地自动化，而是：

- 保留本地研究门户和资料库作为内容层。
- 把采集、调度、生成简报、消息推送迁到云端执行。

## 二、目标状态

目标不是“把所有东西都搬上云”，而是形成三层结构：

1. 内容层
- 保留当前研究资料、公司档案、动态样例、门户页面。
- 继续作为长期沉淀和深度阅读入口。

2. 执行层
- 云端定时运行。
- 负责抓取信息、筛选有效变化、生成日简报和周报。

3. 推送层
- 把结果稳定推到手机端。
- 微信/企业微信/PushDeer/Bark 等只承担提醒和摘要。

这样可以同时满足：

- 稳定推送
- 手机接收
- 保留现有研究系统资产
- 后续可持续扩展

## 三、推荐路线

### 现阶段最推荐

`GitHub Actions + 手机推送通道 + 本地/静态门户`

理由：

1. 成本低，启动快。
2. 足够覆盖每日/每周简报。
3. 不需要立刻维护一台长期在线服务器。
4. 适合当前“先把稳定推送跑通”的阶段目标。

### 后续升级路线

如果后续需要更复杂的能力，再升级到：

`VPS / 云服务器 + 定时任务 + 数据库存储 + 推送服务`

适合升级的场景包括：

- 跟踪公司数量明显增多
- 抓取源显著变复杂
- 需要保存结构化历史数据
- 需要更精细的权限、日志、失败重试和监控

## 四、建议的系统结构

### 1. 研究内容层

保留当前本地项目：

- `长期高潜力公司跟踪系统/`
- `研究门户/`

职责：

- 存放研究框架
- 存放公司完整档案
- 存放动态更新样例
- 存放门户展示文件

这一层不一定要实时运行，但要持续可维护。

### 2. 云端采集与生成层

建议新建一个独立目录，例如：

- `云端研究简报系统/`

职责拆分为四个模块：

1. `sources/`
- 各公司官方来源配置
- 如 IR 页面、新闻稿、财报页、电话会页

2. `collectors/`
- 定时抓取最新信息
- 只抓官方来源和高可信来源

3. `analyzers/`
- 对抓到的内容做去噪
- 提取真正影响长期逻辑、盈利预期、估值框架的变化
- 生成统一结构：
  - 公司
  - 事实
  - 判断
  - 动作
  - 优先级
  - 下一次验证点

4. `publishers/`
- 输出日简报
- 输出周报
- 输出事件流数据
- 推送到手机端

### 3. 推送层

建议采用“双层推送”：

1. 手机通知层
- 只发摘要
- 一句话结论 + 1-3 条关键变化 + 一个链接

2. 正式阅读层
- 门户页
- 或静态网页
- 或一份云端生成的 HTML 简报页

这样微信不会太重，阅读体验也不会被聊天式消息破坏。

## 五、最适合你的推送方案

### 短中期推荐

`GitHub Actions + PushDeer / 企业微信`

推荐理由：

1. GitHub Actions 负责定时执行，解决“电脑不开机就不跑”的问题。
2. PushDeer 或企业微信负责手机推送，接入简单。
3. 后续如果要改成别的推送方式，不会动到研究逻辑本身。

### 不建议一开始就做的事

1. 不建议直接把完整长简报塞进微信。
原因：
- 阅读体验差
- 信息太长
- 后续历史沉淀不清晰

2. 不建议一开始就做超复杂的云服务器系统。
原因：
- 现在最关键的是先稳定跑通
- 不是一开始就追求“大而全”

## 六、建议的数据流

### 每日日报

1. 定时触发
- 工作日晚上 20:00

2. 拉取目标公司来源
- 财报页
- 新闻稿
- IR 页面
- 政策 / 行业关键来源

3. 对比最近 24 小时变化
- 只保留影响长期逻辑的内容

4. 生成结构化结果
- 一句话结论
- 最多 3 条关键变化
- 今日无需动作
- 决策提示
- 明日重点

5. 推送到手机端
- 摘要消息
- 附门户/详情链接

### 每周周报

1. 每周日晚上触发
2. 汇总最近 7 天事件
3. 生成 5 条关键变化
4. 输出观察池状态表
5. 输出下周重点

## 七、门户如何与云端联动

当前门户不用推倒重做。

后续可以按以下方式升级：

1. 门户继续作为展示层
- 首页看最近更新
- 公司页看沉淀后的理解
- 事件页看单条动态详情

2. 云端每次生成新内容后，只更新两类数据
- 事件流数据
- 公司主页里的“当前结论”与“最新动态”

也就是说：

- 门户负责展示
- 云端负责更新

这样能避免以后再手工维护门户内容。

## 八、推荐实施阶段

### 第一阶段：跑通稳定推送

目标：
- 不依赖本地电脑
- 每日/每周稳定收到摘要

范围：
- GitHub Actions 定时执行
- PushDeer 或企业微信推送
- 输出简报文本

这一阶段先不要求门户自动更新。

### 第二阶段：把事件流同步到门户

目标：
- 门户首页最近更新自动变化
- 公司页最新动态自动变化

范围：
- 生成统一 JSON 数据
- 门户前端读取云端产出的结构化数据

### 第三阶段：补财务分析层

目标：
- 公司主页不只看事件，还能看到真实财务数据和估值判断

范围：
- 财务数据表
- 简单估值区间
- 数据更新时间
- 估值方法说明

### 第四阶段：升级成长期运行系统

目标：
- 增加更多公司
- 增加监控日志和失败重试
- 增加历史事件检索与复盘

## 九、当前最推荐的落地组合

如果只选一个最现实、最适合你当前阶段的方案，我建议：

`GitHub Actions + PushDeer + 当前研究门户`

解释：

- GitHub Actions：解决定时稳定执行
- PushDeer：解决手机提醒
- 当前研究门户：继续做深度阅读和研究沉淀

这是最小可行、也最不折腾的升级方式。

## 十、下一步应该做什么

下一步不要同时做很多事，建议按这个顺序推进：

1. 先确定云端执行方案
- 先按 `GitHub Actions` 设计

2. 再确定手机推送通道
- 优先 `PushDeer`
- 备选 `企业微信`

3. 然后搭第一版云端目录结构
- sources
- collectors
- analyzers
- publishers

4. 先跑通“日报”
- 先不碰周报
- 先解决每日稳定产出

5. 日报稳定后，再接门户联动

## 十一、这份方案的核心结论

一句话总结：

- 本地门户继续保留。
- 本地自动化不再作为正式推送系统。
- 正式的执行与推送迁到云端。
- 第一阶段最适合你的方案是：`GitHub Actions + PushDeer + 当前研究门户`。
